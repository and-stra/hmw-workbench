## File formats implemented (`src/assets`, no D3D)

x64-zt does not write plain structs; every asset is a tagged stream (`assetmanager::reader`):

- `u8 type` + (`u8 existing` for containers), `ARRAY`/`RAW` carry a `u32` count/size, `STRING`/`ASSET` carry a
  null-terminated name, `OFFSET` references an earlier item by read-order index + element index. The reader
  implements that table so shared arrays, strings and asset names resolve (the crossbow material list uses
  offsets for repeated materials).
- `.xmb`: raw `XModel` (0x2A8 bytes, `static_assert`ed), name, bone-name hashes + names, parent list, tag
  angles/positions, part classification, base pose matrices, collision/bone info, LOD surface-set names,
  material names, blend-shape/MDAO/composite/bone-physics references.
  - **`parentList` stores the distance back to the parent bone** (`parent = boneIndex - value`), not an absolute
    index. Verified on the crossbow and HMW models (absolute interpretation gives self-parents). Implemented
    in `src/assets/xmodel.cpp`.
  - **`baseMat` is the model-space base pose** (quaternion + position), not a parent-relative pose: all tag
    positions match `tagPositions`, and all `baseMat` translations lie inside the model bounds. World bone
    poses therefore come straight from `baseMat`; the parent-relative local pos/quat shown by `-info` is
    derived with the inverse parent transform.
  - Tags are bones whose name starts with `tag_`; all 17 crossbow tags are dumped correctly.
- `.xsb`: `XModelSurfs` (0x38), name, `XSurface[]` (0x108), then per surface: packed vertices (32 bytes:
  xyz, binormal sign, colour, half2 UV, packed normal, packed tangent), index list, second index list,
  rigid lists + collision trees, unknown0, blend weights + table, lightmap unwrap, tension streams, optional
  subdiv levels, blend shapes. The reader decodes positions, normals, tangents (10:10:10 packed), binormal
  sign and UVs; it stores the raw XBlendInfo weights and 32-byte blend table for M3. LOD0 geometry is kept.
  All other streams are parsed (not skipped blindly) so a bad file fails validation.
- material `.json`: name, technique set, texture table (`image`, `semantic`, `samplerState`). Colour = semantic
  2, normal = 5, specular = 8.
- `.h1Image` + `streamN.pixels`: `GfxImage` (0x68), name, optional embedded pixel array (non-streamed), four
  stream descriptors. For streamed images the highest available `_streamN.pixels` (largest mip) is loaded; the
  file contains the base mip of that stream. The crossbow uses BC1 colour at 2048² (stream3) and BC5 normal at
  2048² (stream3). Textures are uploaded with the dumped DXGI format, one mip level.

## Rendering (`src/render`)

- New model pipeline: per-surface vertex/index buffers, per-material albedo/normal/specular SRVs, one key
  light + ambient + basic specular, tangent-space normal mapping (BC5 z reconstructed), checker for missing
  colour maps, flat normal for missing normal maps, black specular when missing.
- Wireframe rasterizer state (`-wire` / Inspector checkbox), per-surface visibility (Inspector checkboxes).
- Bones/tags overlay with names drawn through ImGui: in the window onto the viewport draw list, in headless
  screenshots onto a headless ImGui background draw list rendered into the scene target. Tags are yellow,
  other bones light blue, selection cyan; bone links are drawn from parent to child.
- Scene grid and model are rendered into the offscreen scene texture, then shown via `ImGui::Image`.

## UI

- Selecting an xmodel in Assets loads it (`.xmb` + LOD0 `.xsb` + materials + textures) and frames it.
- Inspector: model summary (bones/roots/surfaces/verts/tris/bounds/warnings), reload/frame/visible, Bones
  checkbox (+ all-names toggle), Wireframe, bone list (click selects and highlights, tooltip with parent +
  local/world position), surface list with visibility checkbox and material + texture names, material list
  with technique set and textures by semantic.
- Timeline is still the M0 placeholder (M3).

## CLI

```
hmw-workbench.exe -info <xmodel>
hmw-workbench.exe -validate
hmw-workbench.exe -screenshot out.png [-model <xmodel>] [-bones] [-wire]
                  [-width N] [-height N] [-yaw DEG] [-pitch DEG] [-dist N] [-fov DEG]
```

`-info` prints bones (index, name, parent, local pos + quat, world pos), tags, surfaces (verts/tris/material,
blend sizes), materials (techset + textures by semantic) and bounds. `-validate` walks every `xmodel/*.xmb`
in all roots, parses it, all its LOD `.xsb` surface sets, and every referenced material json; it prints one
line per unique failure and a summary, and exits 1 when there are failures (here: missing dump files).

## Open issues

- **No HMW M4 viewmodel in any dump.** `refs\dumps\hmw_patch_common_mp\weapons\h1_m4_mp.json` references
  `wpn_h1_asl_m4a1_vm_camo`, but no `wpn_h1_asl_m4a1_vm_camo.xmb` exists in any asset root (searched all of
  `refs\dumps`, `zonetool\mod`, `GAME\dump`; the M4 materials/images are present, the model is not). The
  requested `info_<HMW M4 viewmodel>.txt` and `m4_orbit.png` could therefore not be produced. As the closest
  available HMW weapon viewmodel the report uses `wpn_h1_melee_combat_knife_vm`:
  `info_wpn_h1_melee_combat_knife_vm.txt` and `hmw_knife_orbit.png`. It parses and renders (geometry only).
  The M4 needs a zonetool dump, which is not part of M1.
- **HMW streamed textures are missing.** The HMW dumps contain `.h1Image` headers with `streamed=1` but no
  `streamed_images\*_streamN.pixels` (e.g. all four knife colour/normal/spec stream files are absent; the
  directory does not exist under `hmw_patch_common_mp`). The knife therefore renders with the checker
  fallback, not textured. The "one HMW weapon viewmodel renders textured" done-criterion is blocked by the
  dump data, not by the reader. The crossbow (from `zonetool\mod`, self-dumped) is fully textured.
- The crossbow also references five material jsons that were not dumped (`mtl_crossbow_scope_base`,
  `mtl_crossbow_target`, `mtl_player_emblem`, `mtl_crossbow_glass_base`, `mtl_iron_sights_color`, plus the
  `ms/mtl_crossbow_scope_base` duplicate), so those small surfaces use checker/fallback material. They are
  reported by `-validate`.
- 46 unique attachment/character models (92 xmb files across the two roots) reference 48 missing LOD
  surface sets (see above); they cannot be previewed until those surface sets are dumped.
- **Skinning**: M1 renders the model-space base pose directly. `baseMat` is model-space, and the raw vertices
  are already in the same space (their bounds match `XModel::bounds`), so no skinning is needed for a static
  preview. Vertex blend weights/table are read and stored but not applied; GPU skinning and animation deltas
  are M3 work. This is a deviation from "skinning done on the GPU" in the M1 description, but the static
  result is correct.
- Bone overlay is 2D and not depth-occluded (drawn as ImGui lines on top of the scene); acceptable for M1,
  could be replaced by a line pass with depth in a later milestone.
- Bone world positions for the animated cable/wheel bones come from `baseMat`; this is a base/animation pose
  that may differ from the bind mesh for skinned parts. The tag positions (the ones needed for M4) are exact.
- `-info` accepts xmodels only. `-weapon`, `-anim`, `-attach`, `-camo`, `-view`, `-bones`/`-wire` are
  implemented only as far as M1 needs (`-bones`/`-wire` for screenshots).
- The material loader uses light-weight semantic heuristics (name contains `col`, `nml`, `spc`) to pick the
  first colour/normal/specular map because H1 material sampler binding (techset arguments) is not decoded
  yet. Good enough for the crossbow; a techset/material argument reader is M6 material work.
- M0's `DirectXTex` build exclusions (D3D12 + GPU BC compression) remain.

## Deviations from the plan

- The requested HMW M4 review artifacts are substituted by the HMW knife because the M4 model is absent
  (see open issues); all other requested file names exist.
- M1 adds `-info`/`-validate` output formats with a few extra fields (tags, world poses, blend sizes,
  warnings) beyond the minimum list.
- `ms/` material names fall back to their `m/` json (observed in the crossbow dump; `ms/mtl_crossbow_base`
  resolves to `m/mtl_crossbow_base.json`).
- Textures are uploaded as base mip only (one level); mip chains are not generated. The dumped stream files
  only carry the base mip of each stream anyway.
- `review/M0/empty.png` was regenerated as part of the coordinate-system fix.
